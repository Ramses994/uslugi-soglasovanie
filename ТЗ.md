# Техническое задание и архитектурное решение
## Веб-сервис «Форма согласования добавления новых услуг и продуктов в прейскурант МИС Медиалог»

Версия документа: 1.0. Целевая МИС: **Медиалог 8.10.04.R (сборка B2060 от 28/11/22)**.
Документ подготовлен для передачи в Cursor как основа для реализации; рядом с ТЗ
поставляется рабочий прототип (бэкенд + фронтенд + тестовые данные), прошедший
smoke-тестирование — см. раздел 12.

---

## 1. Контекст и цель

Сотрудники клиники (врачи, заведующие отделениями, маркетинг, коммерческий блок)
сейчас инициируют добавление/изменение услуг в прейскурант МИС «Медиалог» через
заполнение Excel-формы (`Форма заявка на изменения прейскуранта.xlsx`, листы
«Внесение новой услуги», «Внесение новой комплексной услуги», «Удаление услуги»,
«Введение акции») и её пересылку по почте. Дальше администратор МИС вручную переносит
данные в карточку «Услуга» (см. скриншот карточки, версия 8.10.04.R) — это медленно,
подвержено ошибкам и не даёт видимого статуса согласования.

Цель — веб-форма, которая:

1. Выглядит и ощущается современно (не как Excel/карточка МИС), но по составу полей
   **точно покрывает** карточку «Услуга» МИС Медиалог + деловое обоснование из
   прежней Excel-формы.
2. Автоматически подставляет данные инициатора из AD — исключает ручной ввод ФИО/должности/почты.
3. Для лабораторных услуг — принудительно требует сопоставление со справочником
   **ЕРЛУ-КДЛ** (`ЕРЛУ-КДЛ_13.10.25 (3).xls`, реальная структура файла разобрана в разделе 7.1).
4. Даёт автокомплит по **номенклатуре Минздрава** (НСИ, OID `1.2.643.5.1.13.13.11.1070`,
   файл `1.2.643.5.1.13.13.11.1070_2.10.xlsx`, структура разобрана в разделе 7.2).
5. Маршрутизирует заявку на согласование выбранным согласующим по e-mail.
6. (Ценное расширение поверх исходного запроса, см. раздел 1.1) — как только все
   согласующие подтвердили заявку прямо из письма, генерирует **готовый к загрузке
   файл импорта** в формате, который принимает штатный пункт меню МИС Медиалог
   «Услуги / Импорт прейскуранта услуг» — администратору останется нажать «Импорт»,
   а не набирать поля вручную.

### 1.1 Почему добавлена маршрутизация с кликабельными ссылками и генерация файла импорта

Исходное требование ограничивалось «отправкой заявки по email на согласовантов».
Это создаёт две проблемы, которые устраняет предложенное решение:

- **Нет обратной связи о статусе.** Просто разосланное письмо не отвечает на вопрос
  «согласовано ли уже, кем именно, чего ждём». Решение: каждое письмо согласующему
  содержит две кнопки — «Согласовать» / «Отклонить» со ссылками на одноразовые
  подписанные токены (`itsdangerous`, TTL 14 дней). Клик не требует логина в систему,
  сразу меняет статус заявки и уведомляет инициатора. Полная история решений видна
  в веб-форме (раздел «Мои заявки», список согласований по каждой заявке).
- **Двойной ручной труд.** Даже согласованную заявку администратор МИС должен набрать
  в карточке услуги заново. Реальная документация Медиалог (раздел «Импорт
  прейскуранта услуг», обязательные/дополнительные параметры импорта) описывает
  ожидаемые колонки файла импорта — `CODE, INSURANCE_TYPE, LABEL, SHORT_LABEL,
  DESCRIPTION, SERVGRP_CODE, TAXE_CODE, DEP_CODE, STATE, SEX, SERV_TYPE,
  SERV_EXT_TYPE, PERIODICAL, PRICE_FOR_CHANGE, PRICE_TYPE, INVOICE_TYPE, ORG_CODE,
  DEVISE_CODE, OMS_CODE, MINZDRAV_CODE`. Наша форма уже содержит все нужные данные —
  почему бы не сгенерировать этот файл автоматически по факту согласования и приложить
  его к финальному письму? Реализовано в `backend/app/services/medialog_export.py`,
  проверено на реальном примере (раздел 12.3).

Если это расширение избыточно для первой итерации — оно изолировано в одном модуле
и одном роутере (`routers/approvals.py`) и может быть отключено без переделки
остальной системы (см. раздел 11 «Что можно урезать для MVP»).

## 2. Роли и пользователи

| Роль | Действия в системе |
|---|---|
| **Инициатор** (любой сотрудник с доменной учёткой) | Заполняет и отправляет заявку. Видит статус своих заявок. |
| **Согласующий** (гл. врач, коммерческий директор, гл. бухгалтер, зав. КДЛ, админ МИС — справочник в `data/approvers.json`) | Получает письмо, кликает «Согласовать/Отклонить» без логина в систему (или через веб-форму, если авторизован). |
| **Администратор МИС** | Получает финальное письмо с приложенным файлом импорта, загружает его в Медиалог через «Услуги / Импорт прейскуранта услуг». |
| **Администратор формы** (Phase 2) | Правит список согласующих, филиалов, инициирует принудительное обновление справочников. В прототипе это тот же эндпоинт `/api/dictionaries/reload`, доступный любому авторизованному пользователю — для продакшена нужно завести отдельную роль (см. раздел 10). |

## 3. Функциональные требования к форме

Состав полностью соответствует разделу 3 первоначального запроса; в скобках —
как поле называется в коде (`backend/app/schemas.py::ServiceRequestIn`).

### 3.1 Обязательные поля
1. **Наименование** (`name`) — полное наименование для отображения в МИС.
2. **Тип услуги** (`service_type`): Простая / Сложная / Комплексная / Медпрограмма /
   Пакет услуг / ПРН. Значения синхронизированы с полем `SERV_EXT_TYPE` импорта
   Медиалог (`S/D/P/C/X`, ПРН оформляется как простая услуга + тип направления — см.
   документацию Медиалог, раздел «Импорт типов направлений»).
3. **Цены по филиалам** (`prices[]`, `all_branches`) — чекбокс «Во всех филиалах» либо
   раздельный ввод по каждому из «Куркино», «Каширка», «Куркино 2 (взр.)» (список
   вынесен в `config.Settings.branches`, в проде — из справочника «Внутренние
   медицинские учреждения» МИС, см. раздел 10).

### 3.2 Опциональные поля
Сокращённое наименование, альтернативное название, описание, стандарт лечения, дата
начала/окончания действия, ограничение по полу, ограничение по возрасту (от/до),
контроль повторного оказания услуги в течение дня — все присутствуют в
`ServiceRequestIn` и в UI под сворачиваемым блоком «Дополнительные параметры», чтобы
не перегружать инициатора длинной формой при простом сценарии.

### 3.3 Блок для лабораторных услуг (ЕРЛУ-КДЛ)
Активируется чекбоксом «Это лабораторное исследование / анализ». Обязательные поля:
точное наименование анализа (автокомплит по ЕРЛУ), код лаборатории (подставляется
автоматически при выборе), наименование направления исследования, тип биоматериала.
Реальная структура источника — раздел 7.1.

### 3.4 Сопоставление с номенклатурой Минздрава
Поле автокомплита ищет одновременно по коду (`A03.26.009`) и по названию, срабатывает
и при наборе основного наименования услуги (автоподсказка «похоже, вы имели в виду»),
и по отдельному полю ручного поиска — см. раздел 7.2 по структуре источника.

### 3.5 Маршрутизация
Чекбокс-список согласующих (`data/approvers.json`), кнопка «Отправить на согласование»
→ `POST /api/requests`.

### 3.6 Расширение: деловое обоснование (перенесено из старой формы)
Лист «Внесение новой услуги» исходного `Форма заявка на изменения прейскуранта.xlsx`
содержит поля, которых нет в карточке МИС, но которые нужны согласующим для принятия
решения: вид услуги, продолжительность, персонал, оборудование, расходники,
позиционирование. Перенесены в необязательный блок «Деловое обоснование»
(`ServiceRequestIn.business`), чтобы не терять управленческий контекст, который
раньше заполнялся в Excel.

## 4. Нефункциональные требования

- **Безопасность.** Пароль пользователя из формы логина используется один раз для
  LDAP bind и никогда не сохраняется (ни в БД, ни в токене, ни в логах — см. раздел 6).
  Сессия — httpOnly+secure+SameSite=Lax JWT-cookie. Ссылки согласования — подписанные
  токены с ограниченным сроком действия, невозможно подделать без секретного ключа
  приложения (`itsdangerous.URLSafeTimedSerializer`).
- **Доступность.** Адаптивная вёрстка (Tailwind, брейкпоинты `sm:`), форма пригодна
  для использования с мобильного устройства согласующим, если он не за компьютером.
- **Производительность.** Справочники (2 000–11 000 строк) грузятся в память при
  старте, автокомплит — линейный скан с `SequenceMatcher`, укладывается в единицы
  миллисекунд на такой объём; не требует внешнего поискового движка.
- **Наблюдаемость.** Журнал заявок в БД (`ServiceRequest`) с историей решений
  (`approvals` JSON) — основа для будущего дашборда «сколько заявок висит, у кого».

## 5. Архитектура решения

### 5.1 Стек
- **Бэкенд:** Python 3.11, FastAPI + Uvicorn (асинхронный, автогенерация OpenAPI/Swagger
  на `/docs` — удобно для Cursor и для ручного тестирования эндпоинтов), SQLAlchemy 2.0
  + SQLite (журнал заявок; для продакшена — тот же код работает и на PostgreSQL, меняется
  только `DATABASE_URL`), `ldap3` для AD, `python-jose` для JWT, `itsdangerous` для
  одноразовых ссылок, `openpyxl`/`xlrd` для справочников, `Jinja2` для HTML-писем,
  `smtplib`/`aiosmtplib` для отправки.
- **Фронтенд:** одностраничное приложение без сборщика — HTML5 + TailwindCSS (CDN) +
  Alpine.js (CDN, ~15 КБ). Выбор в пользу Alpine, а не полноценного Vue/React-проекта:
  форме не нужен роутинг и сложное состояние, а разработчику в Cursor не придётся
  разворачивать Node/Vite, чтобы просто открыть и поправить страницу — `index.html`
  можно открыть прямо в браузере поверх работающего бэкенда. При росте требований
  (личный кабинет, история заявок с фильтрами, дашборды) — прямой путь миграции на
  Vue 3 + Vite, компонentная модель Alpine к этому близка.

### 5.3 Прямая интеграция с БД Медиалог — сознательно НЕ делаем в MVP

В `Medialog_SQL_cheatsheet.md` (проектная база знаний) есть таблицы вроде
`DATA_MOTCONSU_BILLDET.FM_SERV_ID` и т.п., что теоретически позволяет писать услугу
напрямую в БД МИС. Мы **не рекомендуем** так делать по трём причинам: (1) прямые
INSERT/UPDATE в проприетарную БД МИС в обход штатного слоя бизнес-логики Медиалог
рискуют нарушить внутренние инварианты (согласованность цен/категорий/прав доступа,
пересчёт зависимых сущностей), (2) при обновлении версии МИС схема БД может измениться
без предупреждения — это встроенная точка отказа, о которой вендор не обязан
уведомлять, (3) у Медиалог уже есть официальный, поддерживаемый вендором способ
пакетного ввода — импорт прейскуранта из файла (раздел 1.1). Наш файл импорта
использует именно этот легитимный путь.

## 6. Интеграция с LDAP / Active Directory

Полный код — `backend/app/auth/ldap_auth.py`. Логика (двухшаговая, без хранения пароля):

```python
def authenticate(login: str, password: str) -> LdapUser:
    server = Server(settings.ldap_server, get_info=ALL)

    # Шаг 1: bind ПОД САМИМ ПОЛЬЗОВАТЕЛЕМ = проверка пароля.
    # AD сам вернёт ошибку при неверном пароле/заблокированной учётке.
    try:
        user_conn = Connection(
            server, user=user_principal, password=password,
            authentication=NTLM if "\\" in login else "SIMPLE",
            auto_bind=True,
        )
    except LDAPBindError as exc:
        raise LdapAuthError("Неверный логин или пароль") from exc

    # Шаг 2: тем же соединением читаем атрибуты профиля.
    search_conn = user_conn
    search_conn.search(
        search_base=settings.ldap_user_search_base,
        search_filter=f"(sAMAccountName={sam_account})",
        search_scope=SUBTREE,
        attributes=["sAMAccountName", "displayName", "mail", "title", "department"],
    )
    entry = search_conn.entries[0]
    return LdapUser(
        login=str(entry.sAMAccountName), display_name=str(entry.displayName),
        email=str(entry.mail), department=str(entry.department), position=str(entry.title),
    )
    # user_conn.unbind() в finally — пароль нигде дальше не хранится.
```

Пароль передаётся с фронтенда на бэкенд **только по HTTPS**, используется один раз для
bind и не логируется (в `routers/auth.py` в лог не пишется тело запроса). Возвращаемый
пользователю токен сессии несёт **атрибуты**, а не пароль:

```python
token = create_session_token(user.login, {
    "display_name": user.display_name, "email": user.email,
    "department": user.department, "position": user.position,
})
response.set_cookie("session", token, httponly=True, secure=True, samesite="lax")
```

Для локальной разработки/демо без боевого AD — `LDAP_MOCK=true` (см. `.env.example`):
любой пароль принимается, профиль строится по таблице `_MOCK_USERS` или генерируется
на лету по логину. Переключение в проде — одна переменная окружения, код аутентификации
менять не нужно.

**Про SMTP «под доменным логином текущего пользователя»** (пункт 2 исходного ТЗ):
реализовано как опция (`SMTP_SEND_AS_USER=true`), но по умолчанию выключено в пользу
варианта с сервисным ящиком + `Reply-To`. Причина: (1) многие корпоративные почтовые
серверы (особенно Exchange Online) отключают Basic/NTLM SMTP-auth для обычных
пользователей в пользу OAuth2 — прямая доменная авторизация может просто не сработать
независимо от корректности кода; (2) хранить/передавать пароль пользователя лишний раз
(даже одноразово, для SMTP) увеличивает поверхность атаки без реальной выгоды — письма
и так подписываются `Reply-To` инициатора, получатель отвечает «как обычно».

## 7. Справочники: реальная структура и обработка

### 7.1 ЕРЛУ-КДЛ (`ЕРЛУ-КДЛ_13.10.25 (3).xls`)

Файл разобран напрямую (2 330 строк, 5 колонок):

| код ЕРЛУ | наименование ЕРЛУ | код лаборатории | наименование лаборатории | Составное исследование |
|---|---|---|---|---|
| 01. | ГЕМАТОЛОГИЯ | *(пусто)* | *(пусто)* | Нет |
| 01.00.001 | СОЭ (по Вестергрену) | 1.0.A1.202 | СОЭ (венозная кровь) | Нет |
| 01.00.002 | Клинический анализ крови без лейкоцитарной формулы и без СОЭ | 1.0.D1.202 | Клинический анализ крови без лейкоцитарной формулы (венозная кровь) | Нет |

Строки-заголовки разделов (например `01.` / «ГЕМАТОЛОГИЯ») отличаются пустой колонкой
«код лаборатории» — `dictionaries.py::load_erlu` распознаёт их и не индексирует как
анализ, но запоминает как `section` для группировки в UI (можно показывать заголовок
раздела над результатами автокомплита). После обработки получилось **1 961 индексируемая
запись** (проверено на реальном файле, раздел 12.1).

### 7.2 Номенклатура медицинских услуг Минздрава (НСИ `1.2.643.5.1.13.13.11.1070`)

Файл `1.2.643.5.1.13.13.11.1070_2.10.xlsx`, лист «Справочник», 10 983 строки:

| ID | S_CODE | NAME | REL | DATEOUT |
|---|---|---|---|---|
| 1422 | A03.26.009 | Офтальмометрия | 1 | *(пусто)* |
| 1641 | A05.23.007 | Стабиллометрия | 1 | *(пусто)* |

`REL=1` и пустой `DATEOUT` — актуальная запись (после обработки — **10 980 активных
записей**, проверено, раздел 12.1). `S_CODE` — это то же значение, что ожидает поле
`MINZDRAV_CODE` при импорте в Медиалог (раздел 1.1) — значит выбор из автокомплита
напрямую попадает в итоговый файл импорта без дополнительного маппинга.

**Важный технический нюанс, найденный при тестировании (раздел 12.1):** у части
выгрузок НСИ Минздрава в XML прописан некорректный `<dimension>` (например, файл
заявляет диапазон `A1:A1`, хотя фактически в листе 10 983 строки). При чтении через
`openpyxl` с `read_only=True` (стандартная рекомендация для больших файлов) это
приводит к тому, что читается **только первая ячейка**, а не весь файл — без явной
ошибки, просто пустой результат. Поэтому `dictionaries.py::load_minzdrav` намеренно
использует обычную (не read-only) загрузку, которая игнорирует битый dimension и
читает по фактическому содержимому листа. Это задокументировано в самом коде —
если в будущем захочется оптимизировать под ещё большие файлы через `read_only=True`,
сначала стоит проверить `<dimension>` в XML вручную.

### 7.3 Обновление справочников без даунтайма
`POST /api/dictionaries/reload` перечитывает оба файла в памяти (блокировка на время
чтения — доли секунды даже на 11 000 строк). Путь к файлам — из `.env`
(`DICT_ERLU_KDL_PATH`, `DICT_MINZDRAV_PATH`), можно завести отдельную точку монтирования
(сетевая папка/S3), куда обновлённые версии кладёт ответственный сотрудник.

## 8. Модель данных

### 8.1 Заявка (Pydantic, `backend/app/schemas.py`)
Полная схема — в файле; ключевая структура для понимания:

```python
class ServiceRequestIn(BaseModel):
    request_type: str                      # new_service | complex_service | delete | promo
    business: Optional[BusinessJustification]  # деловое обоснование (раздел 3.6)

    name: str
    service_type: ServiceType              # simple/complex/combined/program/package/prn
    price_list: PriceListType              # dms/oms/both
    prices: list[BranchPrice]              # [{branch, price}, ...]
    all_branches: bool

    short_name: Optional[str]
    alt_name: Optional[str]
    description: Optional[str]
    treatment_standard: Optional[str]
    date_start: Optional[date]
    date_end: Optional[date]
    sex_limit: Sex                          # all/male/female
    age_from: Optional[float]
    age_to: Optional[float]
    repeat_control_per_day: bool

    is_lab_service: bool
    lab: Optional[LabDetails]               # обязателен, если is_lab_service=True

    minzdrav: Optional[MinzdravMatch]       # code, name, manual_override
    approver_ids: list[str]
```

Валидация на уровне модели (`model_validator`): если `is_lab_service=True`, блок `lab`
обязателен; `age_from` не может быть больше `age_to`.

### 8.2 Журнал заявок (SQLAlchemy, `backend/app/models.py`)
Таблица `service_requests`: `id (UUID)`, `status (pending/approved/rejected/imported)`,
данные инициатора, `payload` (весь `ServiceRequestIn` как JSON — источник истины по
содержанию заявки), `approvals` (JSON-массив `{approver_id, decision, comment,
decided_at}`). БД — журнал/аудит, не источник истины по номенклатуре (это сама МИС).

> **Технический нюанс, на который наткнулись при тестировании (раздел 12.2):**
> SQLAlchemy отслеживает изменения `Column(JSON)` по идентичности объекта, снятой при
> загрузке строки. Если мутировать список `entity.approvals` «на месте» и присвоить его
> же самому себе, история атрибута не покажет отличий и `UPDATE` не отправится — заявка
> молча не обновится. Исправлено через `copy.deepcopy` перед мутацией
> (`routers/approvals.py`). Если в проекте добавятся другие места, где правится JSON-поле,
> держите в голове этот паттерн — либо используйте `sqlalchemy.ext.mutable.MutableList`.

## 10. Фронтенд

Одна страница (`frontend/index.html` + `frontend/app.js`), Alpine.js-компонент `app()`.
Ключевые механики:

- **Логин-экран**, пока нет валидной сессии; после логина форма подставляет
  ФИО/должность/отдел/e-mail в шапку — редактировать их пользователь не может
  (поля вычисляются на бэкенде из AD, на фронтенде только отображаются).
- **Динамический блок ЕРЛУ-КДЛ** — появляется по чекбоксу `is_lab_service`
  (`x-show="form.is_lab_service" x-transition`), поля кода лаборатории/ЕРЛУ
  заполняются автоматически при выборе варианта из автокомплита и защищены от
  ручного редактирования (`readonly`), чтобы исключить рассинхронизацию с
  реальным справочником.
- **Автокомплит с debounce** (300 мс) для обоих справочников — реализован без внешних
  библиотек, через `setTimeout`/`clearTimeout` на самом компоненте (см. `app.js`,
  `debouncedMinzdravSearch` / `searchErlu`).
- **Цены по филиалам**: чекбокс «одинаковая цена везде» либо построчный ввод по
  каждому филиалу; филиал без введённой цены считается «услуга не оказывается в этом
  филиале» и не попадает в `prices[]`.
- **Валидация** — обязательные поля через нативные `required`/`:required` (динамически
  включаются для блока ЕРЛУ, только когда `is_lab_service=true`), плюс серверная
  валидация Pydantic (см. раздел 8.1) как источник истины — фронтенд не единственный
  барьер.

Фрагмент — динамическое поле ЕРЛУ (полный код — `frontend/index.html`):

```html
<div class="card border-amber-200 bg-amber-50/40" x-show="form.is_lab_service" x-transition>

</div>
```

```js
selectErlu(r) {
  this.form.lab.erlu_code = r.erlu_code;
  this.form.lab.erlu_name = r.erlu_name;
  this.form.lab.lab_code = r.lab_code;      // подставляется автоматически
```

филиалов + проверка роли (например, членство в AD-группе `CN=PriceFormAdmins`) — легко
добавляется поверх текущей архитектуры без ломающих изменений.

## 12.4 Вторая итерация: прогон через реальный HTTP, а не только TestClient

`TestClient` из раздела 12.1–12.3 работает в процессе, без сети — это скрыло три
проблемы, которые проявились только при запуске настоящего `uvicorn` и обращении
к нему через реальные HTTP-запросы (curl) с настоящими cookie:

1. **Относительные пути в `.env` ломались при запуске из `backend/`.** README
   предлагает `cd backend && uvicorn app.main:app` — при этом `cwd` становится
   `.../backend`, а `DATABASE_URL=sqlite:///./data/requests.db` и пути к
   справочникам резолвились относительно него, а не корня проекта. Результат —
   `sqlite3.OperationalError: unable to open database file` прямо при старте.
   **Исправлено:** `config.py` теперь вычисляет `PROJECT_ROOT` от расположения
   самого файла (`Path(__file__)`, а не `cwd`) и резолвит все относительные пути
   (`dict_erlu_kdl_path`, `dict_minzdrav_path`, `approvers_json`, `database_url`,
   и путь к самому `.env`) через него — приложение теперь одинаково работает
   независимо от директории запуска.
2. **Отправка писем внутри HTTP-запроса без таймаута и без обработки ошибок.**
   `smtplib.SMTP(host, port)` без `timeout` может зависнуть навсегда, если релей
   недоступен; а необработанное исключение внутри `create_request`/`decide` роняло
   запрос в 500 **уже после** того, как заявка/решение были закоммичены в БД —
   пользователь видел ошибку и мог отправить заявку повторно, хотя она уже была
   создана. **Исправлено:** добавлен `timeout=10` на все SMTP-соединения;
   отправка писем вынесена в `BackgroundTasks` (выполняется после того, как ответ
   уже ушёл клиенту/согласующему), а сбой отправки теперь ловится и пишется в лог
   (`try_send_email` / `try_send_email_with_attachment` в `email_service.py`)
   вместо необработанного исключения.
3. **`routers/approvals.py` создавал `SessionLocal()` напрямую**, в обход
   FastAPI-зависимости `Depends(get_db)`, которую используют остальные роутеры.
   В проде это работало (одна и та же реальная БД), но делает эндпоинт
   непроверяемым в изоляции: тестовая подмена БД через
   `app.dependency_overrides[get_db]` на него не действовала, и клик по ссылке
   согласования на самом деле смотрел в другую базу, чем та, где была создана
   заявка. **Исправлено:** `decide()` теперь принимает `db: Session =
   Depends(get_db)`, как и все остальные эндпоинты — заодно эндпоинт стал
   по-настоящему тестируемым.

## 12.7 Третья итерация: форма была ПОЛНОСТЬЮ ПУСТОЙ без интернета

При попытке снять скриншоты формы headless-браузером страница оказалась
полностью белой. Причина — `index.html` подключал Tailwind и Alpine.js с
публичных CDN (`cdn.tailwindcss.com`, `cdn.jsdelivr.net`). В сети без выхода
в общий интернет (проверено: оба хоста недоступны из тестового окружения)
Alpine.js не загружается вообще — а без него ни один `x-data`, `x-show`,
`x-if`, `x-model` на странице не активируется, и пользователь видит пустой
`<body>` без единой ошибки в интерфейсе (только в консоли браузера).

**Это не гипотетический риск.** Внутренняя сеть клиники, где стоят AD,
внутренний SMTP-релей и сама МИС Медиалог, очень часто вообще не имеет
прямого выхода в публичный интернет с рабочих станций и уж тем более с
серверов — именно из соображений безопасности мед. данных. Форма,
работающая только «если повезёт с сетью», непригодна для такого контура.

**Исправлено:** Tailwind собран статически (`npx tailwindcss ... --minify`
по `frontend/index.html` и `frontend/app.js` как источникам используемых
классов) в `frontend/vendor/tailwind.css`; Alpine.js — просто скопированная
minified-сборка в `frontend/vendor/alpine.min.js`. `index.html` подключает
оба файла локально (`<link>`/`<script src="vendor/...">`), никаких
обращений к внешним хостам в браузере пользователя больше не происходит.
Инструкция по пересборке после правки классов — `frontend/vendor/README.md`.

Заодно исправлен сопутствующий баг: кастомные компонентные классы (`.card`,
`.input`, `.btn-primary` и т.д.) были написаны через `@apply` прямо в
`<style>`-блоке `index.html` — это работает только в режиме Play CDN
(рантайм-JIT `cdn.tailwindcss.com`), а в обычном браузере `@apply` — не
валидный CSS и просто игнорируется. При переходе на статическую сборку эти
классы вынесены в `@layer components` при сборке `tailwind.css`, откуда
компилируются в обычный CSS.

## 12.8 Роль «Администратор формы» (закрывает пункт 3 Roadmap)

Реализовано:
- `UserProfile.is_admin` — вычисляется при логине из `FORM_ADMIN_LOGINS`
  (список логинов через запятую в `.env`; в проде — заменить на проверку
  членства в AD-группе, комментарий в `config.py`) и живёт в самом JWT, без

  (раньше был доступен любому авторизованному пользователю — тоже исправлено).
- CRUD на согласующих и филиалы: `GET/POST/PUT/DELETE /api/admin/approvers`,
  `GET/POST/PUT/DELETE /api/admin/branches`. Хранилище — простые JSON-файлы
  (`services/admin_store.py`), без отдельной таблицы БД: записей единицы-десятки,
  транзакционность некритична для MVP.
- Филиалы вынесены из `.env`-константы в `data/branches.json` (создаётся
  автоматически из `branches_seed` при первом запуске) — именно поэтому их
  теперь можно редактировать через UI, а не только через конфиг и рестарт.
- Фронтенд: вкладка «⚙ Администрирование» (видна только `user.is_admin`) —
  два списка (согласующие, филиалы) с удалением и формой добавления; после
  любого изменения список согласующих/филиалов в форме «Новая заявка»
  обновляется сам, без перезагрузки страницы.

**Баги, найденные и исправленные при реализации:**
- `_slugify()` для автогенерации id при сидировании филиалов резал только
  `[a-zA-Z0-9]` — для кириллических названий («Куркино», «Каширка») это
  давало ПУСТУЮ строку → оба схлопывались в один и тот же id `"item"`,
  ломая уникальность записей в CRUD-хранилище. Исправлено на unicode-aware
  `\w` (matчит кириллицу), id теперь `"куркино"`, `"каширка"` и т.д.
- Фронтендный хелпер `api()` вызывал `res.json()` безусловно, а `DELETE`
  возвращает `204 No Content` без тела — `deleteApprover`/`deleteBranch`
  падали бы с ошибкой парсинга JSON. Добавлена проверка `res.status === 204`.
- CRUD-хранилище (`admin_store`) пишет прямо в файлы по путям из `settings` —
  в отличие от БД, эти пути не проходят через `Depends()`, поэтому тесты на
  CRUD дописывали бы записи в реальные `data/approvers.json`/`branches.json`.
  Исправлено: `tests/conftest.py` копирует `approvers.json` во временный
  файл и подменяет `settings.approvers_json`/`settings.branches_json` через
  `monkeypatch` (это работает, потому что `get_settings()` кэширован
  `@lru_cache` — один и тот же объект `Settings` во всех модулях).

Тесты — `tests/test_flow.py::TestAdminRole` (4 теста: обычный пользователь
получает 403, у админа `is_admin=true`, полный CRUD согласующих, CRUD
филиалов) — все проходят вместе с остальными 14 (итого 18/18).

## 12.9 Четвёртая итерация: боевой AD, читаемые ошибки, подбор согласующих из каталога, авто-код Минздрава

По результатам первого реального прогона на сервере клиники (192.168.2.104,
через собственную копию в Cursor) — заявка на четыре изменения: (1) подготовить
вход под боевой AD (домен MEDKVADRAT, логин `dmartynov`); (2) ошибки и системные
сообщения показывать во всплывающем окне, а не инлайн-текстом (в проверке был
виден баг `[object Object],[object Object]` при отправке заявки); (3) дать
администратору подбирать согласующих из каталога корпоративной почты
`@medkvadrat.ru`, а не вбивать email руками; (4) код Минздрава подставлять
автоматически по совпадению с полем «Наименование услуги».

**1. Всплывающее окно ошибок — и баг `[object Object]`.**
Причина бага: при 422 (ошибка валидации pydantic) FastAPI отдаёт `detail` не
строкой, а МАССИВОМ объектов `{loc, msg, type}`. Старый код фронтенда делал
`throw new Error(body.detail)` — `Error` привёл массив объектов к строке через
`Array.prototype.toString()`, а каждый объект внутри — через
`Object.prototype.toString()`, что и даёт буквально `[object Object],[object Object]`
в интерфейсе. Исправлено: `formatApiErrorDetail()` в `app.js` разбирает три
формы `detail` (строка / список ошибок валидации / прочий объект) в читаемый
текст. Одновременно все точки показа ошибок (`loginError`, `submitError`,
`adminError` — три независимых инлайн-абзаца) заменены на единый
`notify(kind, title, message)` и модальное окно поверх интерфейса (см. разметку
в начале `index.html`, вне `x-if="!user"`/`x-if="user"`, чтобы работать и на
экране логина). Регресс-тест формы ответа — `TestValidationErrorFormat` — не
проверяет фронтенд (для этого нет JS-тестов в проекте), но фиксирует, что
`detail` остаётся списком объектов с `msg`/`loc`, на который опирается
`formatApiErrorDetail()`.

**2. Подбор согласующих из каталога AD.**
Новый эндпоинт `GET /api/admin/directory/search?q=...` (только для админа) —
`ldap_auth.search_directory()`: в боевом режиме ищет в AD под сервисной
учёткой (`LDAP_SERVICE_USER`/`LDAP_SERVICE_PASSWORD` — без них подбор по
каталогу возвращает понятную ошибку, а не 500), фильтр по `LDAP_DIRECTORY_MAIL_SUFFIX`
(например, `@medkvadrat.ru`) исключает служебные учётки без реальной почты. В
`LDAP_MOCK=true` — фиксированный демо-набор (`_mock_search_directory`). На
вкладке «Администрирование» перед формой добавления согласующего — поле
поиска по каталогу; выбор подставляет ФИО/email в поля ниже, которые
по-прежнему можно поправить вручную (это ассистент, не замена ручного ввода —
внешнего партнёра без учётки в AD всё ещё можно добавить руками).

**3. Автоматическая подстановка кода Минздрава.**
Новый эндпоинт `GET /api/dictionaries/minzdrav/suggest?name=...` +
`DictionaryStore.best_minzdrav_match_scored()`. При вводе поля «Наименование
услуги» (`app.js`, `debouncedMinzdravAutoSuggest`/`_doMinzdravAutoSuggest`) —
если бэкенд уверен в совпадении, код подставляется сам (чип с пометкой
«подобрано автоматически», крестиком снимается, полноценный ручной
fuzzy-поиск через отдельное поле никуда не делся). Не перезаписывает то, что
выбрано вручную (`manual_override: true`) или явно отклонено крестиком.

**Найденный при живой проверке баг производительности (важно для будущих
правок этого файла):** первая версия `best_minzdrav_match_scored` переиспользовала
ту же формулу скоринга, что и обычный поиск, включая `SequenceMatcher.ratio()`
как фоллбэк для записей без прямого вхождения подстроки — то есть **полный
линейный скан по ~11000 строкам справочника Минздрава с нечётким сравнением
почти для каждой** (те, что не совпали по подстроке). Один такой скан — не
проблема (десятки мс на дешёвом пути, но до ~0.6с если совпадений по подстроке
нет вообще — например, гипотетическое общее слово). Проблема начинается, когда
на **том же поле** висело ещё и заполнение обычного выпадающего списка
(`debouncedMinzdravSearch`, тоже full-scan с той же ценой) — при вводе имени
услуги оба обработчика запускались почти одновременно, оба одинаково дорогие,
и поскольку FastAPI выполняет sync-эндпоинты в пуле потоков под GIL, два
одновременных CPU-bound скана НЕ распараллеливаются, а практически
сериализуются — суммарное время ответа удваивалось (~1.2с вместо ~0.6с,
замерено `curl`, воспроизведено и через реальный ввод в браузере — из-за этого
поначалу казалось, что автоподсказка вообще не срабатывает, хотя запрос
просто не успевал вернуться за то время, что я ждал в проверке). Исправлено
двумя правками: (а) `best_minzdrav_match_scored` больше не использует
`SequenceMatcher` — только дешёвую проверку подстрокой (~10-70 мс на скан);
это не только быстрее, но и безопаснее для АВТОМАТИЧЕСКОЙ (без подтверждения
пользователем) подстановки — нечёткое совпадение без клика человека это
скорее риск подставить не тот код, чем полезная догадка; (б) с поля
«Наименование услуги» убран вызов `debouncedMinzdravSearch()` — выпадающий
список для РУЧНОГО поиска остался только на отдельном поле «Код Минздрава»,
где он и был задуман изначально. Полноценный fuzzy-поиск (`search_minzdrav`,
используется и там) не трогали — он остаётся быстрым при обычном
использовании (один клик — один запрос), просто дорог для двух параллельных
full-scan'ов на каждое нажатие клавиши.

**Ещё один найденный по пути инфраструктурный баг: забытая пересборка
Tailwind.** Все три новых куска разметки (модальное окно, чип авто-подсказки
Минздрава, поиск по каталогу AD) используют классы (`fixed`, `inset-0`,
`z-50`, `bg-slate-900/40`, `list-disc`, `list-inside`, `min-w-0` и т.д.),
которых не было в `frontend/index.html`/`app.js` на момент последней сборки
`frontend/vendor/tailwind.css` (см. раздел 12.7 — статическая сборка включает
только классы, реально встречавшиеся в разметке НА МОМЕНТ сборки). Из-за этого
модальное окно при первой живой проверке было в DOM (`notice.open === true`,
текст ошибки присутствовал), но визуально не появлялось и не было зафиксировано
поверх экрана — рендерилось как обычный блочный элемент у верха страницы, а
не `position: fixed` поверх всего, и терялось из виду при любом скролле формы.
Обнаружено не чтением кода, а измерением реальных координат элемента в
браузере (`boundingBox()` показал `y: -556` при `scrollY: 581` — верный
признак, что `position: fixed` не применился). Исправлено пересборкой
`tailwind.css` по инструкции из `frontend/vendor/README.md` — **это тот самый
сценарий, о котором предупреждает сам README**: если он не был перечитан
после правки разметки, регрессия воспроизведётся снова.

**4. Подготовка к боевому AD (домен MEDKVADRAT).** Без доступа к реальному
контроллеру домена клиники проверить bind невозможно из этой среды — ниже
только то, что можно было проверить статически (по коду) и что было
исправлено как гарантированный баг, плюс чек-лист диагностики для первого
реального запуска (см. `cursor_update_prompt.md`):
- Баг: UPN для входа голым логином (без `@`/`\`) строился как
  `f"{login}@{ldap_domain}.local"` — жёстко зашитый суффикс `.local`. Для
  домена, чей DNS-суффикс НЕ `.local` (например, `medkvadrat.ru`), это давало
  заведомо неверный UPN и провал bind'а даже с верным паролем. Исправлено:
  отдельная настройка `LDAP_UPN_SUFFIX` (по умолчанию `clinic.local` для
  демо-совместимости, для MEDKVADRAT — `medkvadrat.ru`).
- Добавлена поддержка LDAPS/`LDAP_USE_SSL` — многие AD, начиная примерно с
  патчей 2020 г., по умолчанию требуют LDAP signing/channel binding для
  simple bind; обычный `ldap://` в таком случае AD отклоняет как «неверный
  пароль» ДАЖЕ ПРИ ВЕРНОМ пароле, что легко принять за опечатку. Рекомендация
  в `.env.example` — сразу использовать `ldaps://`.
- `search_directory()` (подбор согласующих, см. выше) переиспользует ту же
  `_make_server()` и требует `LDAP_SERVICE_USER`/`PASSWORD` — без них подбор
  по каталогу в боевом режиме недоступен (понятная ошибка, не 500).

Тесты — `tests/test_flow.py::TestDirectorySearch` (4), `TestMinzdravAutoSuggest`
(3), `TestValidationErrorFormat` (1) — новые 8, итого 26/26. Реальный bind в AD
MEDKVADRAT тестами не покрыт и не может быть — нет доступа к сети клиники из
среды разработки; это первое, что нужно проверить руками при следующем
живом прогоне (чек-лист — `cursor_update_prompt.md`).

## 13. Развёртывание

Минимальный вариант — один процесс `uvicorn` за reverse-proxy (Nginx/IIS ARR) с TLS:

```
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2
```

FastAPI отдаёт и API, и статику фронтенда (`StaticFiles` на `/`, см. `main.py`) — не
нужен отдельный веб-сервер для фронтенда в простом развёртывании. Для более высокой
нагрузки — вынести `frontend/` на отдельный статический хостинг/CDN и указать
`API_BASE` в `app.js`.

Переменные окружения — через `.env` (пример — `.env.example`), либо через переменные
процесса/секреты оркестратора при контейнеризации.

### 13.1 Готовый вариант — Docker на Linux-сервере

В репозитории есть `Dockerfile` и `docker-compose.yml`. Важные решения, зафиксированные
в них (чтобы при доработке их не «улучшили» по незнанию контекста):

- `data/` монтируется как bind-volume (`./data:/app/data`), а не запекается в образ —
  `approvers.json`/`branches.json` редактируются через вкладку «Администрирование»,
  `requests.db` растёт при подаче заявок; всё это должно переживать `docker compose up
  --build`/пересборку образа при обновлении кода.
- Порт наружу задаётся переменной `APP_PORT` в `.env` (`ports: - "${APP_PORT:-8000}:8000"`),
  по умолчанию **8000**. Раньше здесь был захардкожен `80:8000` в расчёте на
  `http://<хост>` без порта в адресе — это оказалось неверным предположением
  на практике: при первом реальном деплое на 192.168.2.104 порт 80 уже был
  занят Zabbix (`monitoring-zabbix-web-1`), и жёстко прописанный `80:8000` в
  `docker-compose.yml` при каждом обновлении из репозитория стирал ручную
  правку на `8000:8000`. Теперь порт — переменная окружения: правка `.env`
  переживает `git pull`, а сам `docker-compose.yml` обновлять не нужно. Если
  на каком-то сервере 80 всё-таки свободен — добавить `APP_PORT=80` в `.env`
  этого сервера. Если 80 занят и НЕ должен освобождаться (как здесь) —
  оставить порт как есть или добавить отдельный reverse-proxy на 80, не
  трогая сам compose-файл.
- `.env` передаётся через `env_file`, не коммитится (см. `.gitignore`) и не запекается
  в образ — при первом деплое на боевой сервер `LDAP_MOCK` нужно осознанно выставить
  `false` и заполнить реальные `LDAP_*`/`SMTP_*` только когда есть подтверждённые
  боевые креды AD/SMTP; до этого сервис можно поднять с `LDAP_MOCK=true` для проверки
  UI/доступности по сети — это не то же самое, что боевая готовность.
- Healthcheck дергает `/api/health` изнутри контейнера — `docker compose ps` показывает
  реальное состояние процесса, а не только «контейнер запущен».

формате, ожидаемом именно вашей настройкой импорта прейскуранта (это единственное
